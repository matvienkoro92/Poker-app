# Повторный аудит текущего проекта

Дата: 5 сентября 2026. Объект: локальное рабочее дерево после двух этапов исправлений, включая незакоммиченные изменения. Production и реальные персональные данные не использовались. В рамках аудита код приложения не исправлялся.

Статус после исправлений: см. [отчёт об устранении замечаний](2026-09-05-audit-fixes.md). Ниже сохранены исходные результаты аудита.

## Вывод

Сборка и основные сценарии работают. Улучшения авторизации и мобильного старта подтверждены, предупреждений npm audit нет. Однако бонусный учёт пока нельзя считать полностью устойчивым к повторным запросам, отказам чтения и росту истории. Два дефекта воспроизведены отдельно от рабочего Redis; ещё несколько подтверждены анализом конкретных путей исполнения.

Моя прежняя формулировка о надёжности бонусных операций была слишком широкой: атомарность записи закрывает частичное сохранение, но не равнозначна идемпотентности и достоверности отчётов.

## P1. Повтор ручной операции повторяет начисление или списание

Файлы: lib/api-handlers/admin.js:560; lib/bonus-ledger.js:58, 589.

Обработчик ручных бонусов не получает уникальный идентификатор запроса. sourceId содержит ID администратора, а запись журнала каждый раз получает случайный ID. Блокировка действует только на одновременность записи: второй последовательный запрос успешно изменяет баланс снова.

Воспроизведение на изолированном настоящем Redis: два вызова addBonusOperation с одинаковыми userId, amount=10, operationType и sourceId дали баланс 20. Это особенно опасно, когда первая операция уже сохранена, но клиент не получил ответ и повторяет действие. Наличие кнопки с disabled в интерфейсе не защищает от этого сценария.

Исправление: клиентский operationId; проверка и сохранение результата в том же Lua-скрипте, что меняет баланс; повтор возвращает исходный результат. Один operationId с другим содержимым должен отклоняться. Проверки: последовательный повтор, конкурентный повтор, потеря ответа после успешной записи.

## P1. Отказ чтения Redis выглядит как корректный отчёт с нулевыми списаниями

Файлы: lib/bonus-ledger.js:358–370; также чтения в getBonusLedgerExpenseRangeSummary, начиная с 518.

Для MGET записей журнала не установлен throwOnError. Ошибка pipeline превращается в null, затем в пустой массив. Формирование отчёта продолжается; часть операций пропускается. Аналогично обрабатываются некоторые чтения списка ID и отметок возврата.

Воспроизведение: после фактического списания 5 искусственно отказал только MGET. getBonusLedgerRangeSummary завершилась без исключения и вернула debitedDuringRange=0. Остаток при этом прочитан, поэтому ответ выглядит правдоподобно, хотя движения денег неверны.

Исправление: обязательные чтения отчёта должны быть строгими; при неполном наборе данных вернуть ошибку/признак недоступности и не кэшировать результат как полный. Проверки: отказ первого/среднего чанка, отказ HMGET возвратов, отсутствие записи по ID.

## P1. История расчётов ограничена последними 5000 операциями

Файлы: lib/bonus-ledger.js:126–129, 315–323; lib/api-handlers/promo.js:1369.

Глобальный индекс журнала обрезается до 5000 ID, персональный — до 500. Отчёты по выбранным датам рассчитываются по этому глобальному индексу. При достаточной активности начало выбранного периода выпадает из индекса, но результат по-прежнему выдаётся без признака неполноты. Отдельные JSON-записи сохраняются, однако стандартный путь построения отчёта их уже не находит.

Это условный дефект масштаба, подтверждённый кодом; количество записей в рабочей базе не проверялось. Он не означает, что текущие реальные отчёты уже ошибочны.

Исправление: постоянный индекс по времени с пагинацией или дневные агрегаты и архив журнала. Пока этого нет — возвращать границу доступной истории и запрещать выдачу заведомо неполного отчёта как полного. Проверка: 5001+ операция с запросом диапазона, включающего самую старую.

## P2. Подтверждение кода и установка пароля выполняются несогласованно

Файлы: lib/api-handlers/auth-email.js:141–164; lib/api-handlers/auth-pwa-code.js:291–329.

В email-пути код удаляется до проверки/сохранения пароля. Например, непустой пароль короче 6 символов приводит к ошибке уже после удаления рабочего кода; сбой Redis при сохранении создаёт аналогичный результат. Пользователь вынужден заново запрашивать код, расходуя ограниченное число отправок.

В Telegram-пути порядок обратный: сначала сохраняется пароль, затем код удаляется обычным pipeline, результат которого не проверяется. Кроме того, два параллельных запроса способны прочитать один код до его удаления. Ограничитель попыток уменьшает частоту, но не делает код атомарно одноразовым.

Исправление: проверять формат пароля до побочных эффектов; подготовить хеш, затем атомарно сравнить действующий код, сохранить хеш и отметить код использованным. Для сложного email-link сценария нужен явный протокол состояния и безопасного повтора. Не трактовать этот вывод как доказательство входа без знания кода: такой обход не обнаружен.

## P2. Нет индивидуального отзыва долгоживущей PWA-сессии

Файлы: lib/poker-pwa-session.js:8, 35–61; lib/account-password.js:38–49.

Сессия действует 180 дней. Проверка смотрит на подпись и срок, изменение пароля не меняет версию сессии и не отзывает старый токен. При утечке токена смена пароля сама по себе не прекращает доступ. Удаление административных прав из актуального списка уже учитывается отдельно — это улучшено, но обычный пользовательский доступ остаётся.

Исправление: sessionVersion или индивидуальный реестр сессий; увеличение версии при смене пароля/команде «выйти везде», ограниченный срок и обновление токена. Реальной утечки в ходе аудита не установлено.

## P2. Сборка пропускает ошибки CSS

Файлы: scripts/minify-public.js:13–22; например styles-pwa.css:937 и границы styles-home-shell.css.

Отдельный прогон esbuild по исходным CSS дал 37 предупреждений в 20 файлах. Есть незакрытые блоки и обрывки деклараций на границах файлов. minify-public.js не проверяет result.warnings. Браузер восстанавливает синтаксис и отбрасывает часть повреждённых правил; зелёный release-check не означает, что весь CSS разобран корректно.

Из этого не следует, что все 20 файлов визуально сломаны: основные экраны прошли проверку. Риск проявляется при редких состояниях, изменении порядка загрузки и дальнейшем объединении файлов.

Исправление: восстановить синтаксические границы по исходному намерению правил; добавить CSS-проверку в CI, сначала с явным списком существующих исключений, затем без исключений. Не склеивать такие файлы в один CSS до исправления.

## Перед публикацией: обновление версий ресурсов

Файлы: sw.js:197–230; scripts/pre-push:1–5; index.html.

У изменённых JS/CSS во многих местах остались прежние query-версии. Service Worker отдаёт закэшированный вариант versioned code и обновляет его в фоне. Поэтому первый запуск после публикации может смешать новый HTML со старым кодом. Hook намеренно не обновляет версии автоматически.

Это пункт подготовки релиза, а не утверждение о уже произошедшем сбое: публикации в этой работе не было. Перед ней необходимо выполнить контролируемое обновление версий и проверить обновление уже установленной PWA, включая возвращение из офлайна. Простого теста в чистом браузере недостаточно.

## Продукт, UX и производительность

Положительное: главный экран стабилен по геометрии, новости больше не толкают страницу, основная иллюстрация облегчена, переходы и открытие окон проверены. Фоновая загрузка неоткрытых разделов отключена; первый переход в них теперь честно зависит от сети, поэтому загрузочные состояния и повтор после ошибки важнее прежнего.

Последний лабораторный прогон предыдущего этапа: FCP 2,61 с, LCP 3,14 с, сумма сдвигов 0,00062, DOMContentLoaded 7,28 с. В этом аудите мобильный замер повторно не запускался. Он использует гостя, подменённые API, отключённый Service Worker и Chromium-эмуляцию. Это не проверка Telegram WebView, Safari, установленной PWA или скорости рабочего API. Показатель cls в скрипте — сумма сдвигов за окно замера, а не полноценная реализация расчёта максимального сессионного окна метрики CLS. На длинные задачи приходится около 718 мс превышения 50-мс порога; выполнение JS остаётся следующим направлением оптимизации.

Продуктовые показатели (удержание, конверсия входа, участие в играх) этим аудитом не оценивались: пользовательской аналитики и интервью не было. Численную оценку качества продукта по одному репозиторию давать некорректно.

## Что проверено сейчас

- Полный npm run release:check завершился с кодом 0: сборка, синтаксис, 97 smoke-проверок, бюджеты, API-контракты, 64 модульных теста, расширенная административная навигация и визуальные проверки.
- Свежий npm audit: 0 уязвимостей, включая devDependencies. Это статус базы известных уязвимостей зависимостей, а не гарантия безопасности приложения.
- Тесты настоящего Redis прошли. Поверх них во временном скрипте воспроизведены два описанных дефекта. Рабочая база не использовалась.
- Отдельно проверены предупреждения парсера CSS.
- Полная сборка APK по-прежнему не подтверждена: Java отсутствует. Ранее проверены cap sync и генерация Android-иконок.
