# Chat Push DM Summary — 2026-04-19

Проект: `poker-club-miniapp`

Главная задача этого цикла:

- по клику на push-уведомление с личным сообщением пользователь должен попадать сразу в нужный DM с отправителем

Сопутствующие цели:

- не сломать доставку push в iPhone PWA
- сохранить cold-open сценарий рабочим
- убрать временный шумный debug overlay после завершения отладки

- экран больше не падает в список диалогов как финальное состояние
- шапка DM догружается отдельным hydrate path
- экранный debug overlay убран
- временный trace-слой очищен

Финальная версия на конец цикла:

- `1.827`
- ветка: `main`
- коммит: `d94ce23` — `Clean up temporary push DM trace helpers`

## С чем столкнулись

На старте цикла реальное поведение было таким:

- push приходил
- по клику открывался раздел `Чаты`
- приложение доходило до списка диалогов
- нужный DM не закреплялся

Параллельно была ещё одна проблема:

- push-доставка на iPhone PWA временами залипала
- уведомления не пропадали навсегда, а доходили с задержкой

Это важно, потому что по ходу работы пришлось разделить две проблемы:

1. доставка push
2. handoff из push в конкретный DM

Главный вывод:

- delivery и DM-open оказались разными проблемами
- aggressive repair subscription flow вредил доставке
- основная незакрытая ошибка жила уже в UI/chat-init/state-machine части открытия DM

---

## Что подтвердили логами

Ниже факты, которые были подтверждены, а не просто предположены.

### 1. Канал push живой, но нестабильный

- push не были окончательно сломаны
- после периодов тишины они приходили позже
- значит канал доставки существовал, но работал с лагом

Практический вывод:

- нельзя было дальше агрессивно трогать подписку, `service worker` и re-subscribe flow

### 2. Deep-link target до клиента доходил

В логах стабильно был виден `pending=tg_...`.

Это означало:

- sender/peer id не терялся
- `with=<peer>` реально доходил до клиента
- проблема не в notification payload

### 3. Код открытия DM реально вызывался много раз

В логах много раз появлялись попытки вида:

- `pending-dm`
- `openPendingNoContacts`
- `openConv-direct`
- `setView-chat-post-refresh-open`

То есть проблема была не в том, что код “не пытался открыть чат”.

### 4. Финальным победителем долгое время был список диалогов

Ключевой повторяющийся симптом:

- UI приходил в `view=chat`
- `tab=dialogs`
- `conv=0`

Потом трассировка сузила виновников ещё сильнее:

- сначала `showDialogs-commit`
- потом конкретно `caller=setTab:dialogs`
- потом ещё уже: `caller=setTab:personal-no-with`

Это и стало точкой, где пошли уже не общие guard’ы, а узкие фиксы по реальным caller’ам.

## Какие гипотезы проверяли и что из этого вышло

### Гипотеза A. Ломается `notificationclick` / `sw.js`

Проверяли:

- передачу `openUrl`
- deep-link через `?startapp=club_chat_dm&with=<peer>`
- фокус existing client
- навигацию opened client

Вывод:

- это не был главный корень бага
- payload до клиента доходил

### Гипотеза B. Pending deep-link теряется слишком рано

Проверяли:

- сохранение pending state
- late flush после готовности chat exports
- reopen после `initChat`
- reopen после `chatRefresh`
- post-refresh reopen

Вывод:

- ранние гонки действительно были
- часть их удалось закрыть
- но даже после этого UI всё ещё падал в dialogs

### Гипотеза C. Контакты/диалоги не успевают догрузиться

Проверяли:

- fallback path без готового contacts list
- `openPendingNoContacts`
- bootstrap chat-screen
- загрузку contacts/general в фоне

Вывод:

- это было частью проблемы
- но не последней точкой сбоя

### Гипотеза D. Проблема только в `chatRefresh()`

Проверяли:

- anti-rollback guards в `chatRefresh`
- forced peer lock
- post-refresh reopen

Вывод:

- `chatRefresh` действительно участвовал в откате
- но не был единственным финальным виновником

### Гипотеза E. Push-path идёт не тем путём, что обычный user-flow

Это была главная рабочая гипотеза во второй половине цикла.

Что увидели:

- direct shell open сам по себе не гарантировал устойчивый DM state
- normal-flow через dialogs местами цеплял не тот context
- push-open и обычный open из списка были смешаны слишком сильно

Финальный вывод:

- для push нужен отдельный, более жёсткий path открытия
- но с последующей догрузкой header/meta

## Что реально помогло

Ниже не все промежуточные попытки, а именно то, что в итоге дало рабочий сценарий.

### 1. Разделили delivery и handoff

Самое важное организационное решение цикла:

- перестали дальше aggressively чинить push subscription flow
- зафиксировали более осторожную delivery-конфигурацию
- отдельно продолжили чинить только open-to-DM

Это сняло путаницу, когда две разные проблемы маскировали друг друга.

### 2. Перестали разрешать `dialogs` выигрывать, пока pending ещё жив

Последовательно были перекрыты rollback-path:

- `showDialogs()`
- `showList()`
- `chatRefresh()`
- `setTab("dialogs")`
- `setTab("personal")` при пустом `chatWithUserId`

Это было критично, потому что раньше UI успевал закоммитить список, даже когда `pending=tg_...` ещё жил.

### 3. Push-open перестали вести через обычный dialogs-flow как основной путь

Раньше часть логики пыталась открыть DM через normal route, который лучше работал для обычного тапа из списка, но для push давал:

- wrong dialog hop
- поздний rollback
- зависимость от промежуточного списка

В итоге push-path был переведён на прямой `hard` open:

- `pokerOpenPushDmHard(...)`

Именно это стало ключевым шагом к реальному попаданию в нужную личку.

### 4. Подтянули `chatWithUserId` напрямую из pending deep-link

После трассировки выяснилось, что один из последних узких сбоев был таким:

- `setTab("personal")`
- `chatWithUserId` ещё пустой
- код сам же уходит в `showDialogs()`

Это было исправлено прямым чтением из:

- `window.__pendingOpenChatPersonalFromDeepLink`

И принудительным reroute обратно в hard-open path.

### 5. Отдельно догрузили шапку уже после успешного открытия DM

Когда основной handoff заработал, всплыл финальный хвост:

- чат открывается правильно
- но в шапке сначала виден сырой `tg_...`
- `P21`, имя и avatar не всегда успевают прийти к первому кадру

Для этого был добавлен отдельный post-open hydrate:

- сначала из contacts cache
- потом через `loadContacts({ metaOnly: true })`
- затем через `api/users?userId=...`
- потом дополнительно из payload самого личного чата:
  - `data.contactName`
  - `data.chatDisplayName`
  - `data.userName`
  - fallback из последнего входящего `message.fromName`

Это отделило проблему открытия от проблемы метаданных шапки.

## Что не сработало или оказалось ложным направлением

### 1. Агрессивный repair push-подписки

Попытки force-repair после boot/visibility дали плохой эффект:

- delivery становилась более капризной

Итог:

- этот путь был откатан

### 2. Надежда на один только direct shell open

Простой shell-switch в personal/conv без дальнейшего устойчивого state path оказался недостаточным.

Итог:

- потребовался более жёсткий open path
- плюс anti-rollback guards

### 3. Ставка только на normal-flow через dialogs

Для push это тоже оказалось ненадёжным:

- мог цепляться не тот диалог
- было слишком много зависимости от промежуточного состояния списка

Итог:

- push-path пришлось отделить от обычного open-from-list

## Технический итог

На конец цикла рабочая схема такая:

1. Push приходит в PWA.
2. Deep-link c `with=<peer>` сохраняется как pending target.
3. При cold-open UI больше не должен отдавать победу списку диалогов, пока pending жив.
4. Push-handoff открывает именно нужный DM через hard path.
5. После открытия отдельно догружаются:
   - title
   - `P21`
   - avatar

## Результат

Что достигнуто:

- основная задача решена
- по клику на push пользователь попадает в нужную личку
- проблемы с откатом в список диалогов закрыты
- диагностический шум с экрана убран
- временные trace-хвосты очищены

Что осталось как residual risk:

- delivery push на iPhone PWA исторически была нестабильной по времени доставки
- но это отдельный слой, не связанный напрямую с уже починенным DM handoff

## Практические цели на следующий этап

Если возвращаться к этой теме позже, разумные цели уже не про handoff, а про качество:

1. Убедиться, что имя/аватар в шапке корректно подтягиваются для всех типов peer, а не только для типового кейса.
2. При желании упростить текущую push-DM логику и убрать часть защитных веток, которые уже не нужны после стабилизации.
3. Отдельно, если понадобится, разбирать нестабильность delivery на iPhone PWA, не смешивая её снова с логикой открытия DM.

## Короткий вывод

Этот цикл начался с ощущения, что “push вроде приходит, но чат всё равно не открывается”.

Финально удалось установить, что:

- проблема была не в payload
- не в потере `with=<peer>`
- и не только в `chatRefresh`

Корневой practical issue сидел в cold-open state machine:

- pending target жил
- но UI всё равно разрешал списку диалогов побеждать

После перевода push-open на отдельный hard path, блокировки rollback-веток и отдельной догрузки header-meta сценарий удалось довести до рабочего состояния.
