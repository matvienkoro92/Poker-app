# Auth / Language / Profile Summary — 2026-04-23

## Назначение

Этот файл фиксирует итоговое состояние работ по:

- авторизации в PWA, вебе и Telegram Mini App;
- переключателю языка `RU / EN`;
- профилю пользователя;
- связанным регрессиям, которые ловились по пути.

Файл не заменяет историю коммитов, а даёт короткую инженерную картину состояния проекта на текущий момент.

## Что было сделано

### 1. Единый auth-screen

В проекте закреплён отдельный auth-screen поверх приложения.

Что важно:

- PWA использует отдельный overlay-экран входа;
- веб-версия тоже использует этот overlay-экран;
- Telegram Mini App переведён на тот же fullscreen auth-screen вместо старого верхнего inline-баннера.

Практический эффект:

- вход по почте и Telegram открывается в одном и том же сценарии;
- guest-flow и verified-flow лучше синхронизированы;
- навигация назад внутри auth-flow теперь работает и в веб-версии.

### 2. RU / EN

Переключение языка больше не ограничено только auth-screen.

На текущий момент `RU / EN` влияет на:

- auth-screen;
- профиль;
- шапку приложения;
- главную страницу;
- основные CTA;
- нижнюю навигацию.

Отдельно добавлено:

- переключатель языка в профиле;
- визуально он приведён к тому же стилю, что и на auth-screen;
- при смене языка приложение делает reload, чтобы новый locale стабильно применялся к уже смонтированным экранам.

Ограничение текущего состояния:

- это ещё не полная i18n-система всего приложения;
- в проекте остаются экраны и строки, которые пока не переведены глобально.

### 3. Профиль

По профилю в этом цикле закреплены такие правила:

- guest приравнен к неверифицированному пользователю;
- для guest/неверифицированного профиля скрываются лишние поля;
- оставляется только упрощённый сценарий входа;
- верхняя лишняя кнопка входа убрана;
- layout профиля для guest упрощён.

Дополнительно:

- блок `Уведомления (PWA)` скрывается в обычной веб-версии;
- он должен оставаться только для реально установленной PWA;
- в Telegram Mini App этот блок тоже не показывается.

### 4. Имя в приветствии

Был пойман отдельный регресс:

- при наличии сохранённого имени профиля хедер всё равно мог показывать Telegram username;
- причина была в том, что имя профиля не всегда переживало перезагрузку и часть серверных ответов.

Что закреплено сейчас:

- имя профиля сохраняется локально;
- приветствие в header берёт имя профиля раньше Telegram login;
- fallback к Telegram username остаётся только если нормального profile display name действительно нет.

### 5. Email / Telegram auth-потоки

В этом цикле стабилизированы ключевые auth-сценарии:

- email login / email register;
- Telegram login / Telegram register;
- back-navigation внутри этих сценариев;
- отображение success/error состояний;
- отдельный шаг подтверждения email-кода без преждевременной привязки проверки к паролю.

## Важные инженерные выводы

### 1. Не смешивать overlay auth и старый inline banner

Подтверждённый вывод:

- если overlay auth-screen уже открыт, нельзя позволять старым mini-app/banner веткам повторно монтировать auth в другой контейнер;
- иначе появляются пустые экраны, нерабочие back-кнопки или “залипание” на логотипе.

### 2. Язык должен быть global state, а не частная настройка auth-screen

Подтверждённый вывод:

- одна только смена класса активной кнопки ничего не даёт;
- язык должен жить в одном persistent key;
- после смены языка нужен принудительный refresh UI, иначе часть старых DOM-узлов остаётся в прошлой локали.

### 3. Display name должен переживать reload

Подтверждённый вывод:

- если display name хранится только в runtime-переменной, хедер рано или поздно откатится к Telegram username;
- для приветствия нужен устойчивый источник, который не теряется между запросами и reload.

## Рабочее правило на будущее

Для таких прод-фиксов в проекте закреплено правило:

1. каждый отдельный фикс поднимает `data-app-version` на `+0.001`;
2. каждый фикс идёт отдельным коммитом;
3. каждый фикс сразу пушится в `main`;
4. в документации фиксируется только итоговое рабочее состояние, а не вся шумная цепочка промежуточных гипотез.
