## Что чинили в этом цикле

В этом цикле были две отдельные задачи вокруг chat UI:

1. Починить friend-actions в списке чатов (`+` / `−`).
2. Довести iPhone iOS PWA keyboard path до рабочего состояния:
   - последнее сообщение должно сразу вставать над строкой ввода;
   - сообщение не должно оставаться наполовину перекрытым composer;
   - лишний debug overlay должен быть убран после завершения отладки.

- итоговая посадка последнего сообщения поджата ближе к строке ввода;

## Коротко о найденных причинах

### 1. Friend-actions ломались не в DOM и не в API

Кнопки `+` / `−` в списке чатов обрабатывали клик нормально, но remove-path падал до запроса на сервер.

Реальные причины:

- helper `pokerDebugChatFriendAction` был недоступен из глобальных friend-helper функций;
- helper `peerChatIdsEqual` тоже использовался вне исходного scope.

Следствие:

- optimistic remove-path рвался ещё до `fetch("/api/friends")`;
- визуально казалось, что кнопка "ничего не делает".

### 2. iOS PWA path считала положение ленты слишком грубо

Главная проблема уже не была в самой кнопке или в одном CSS offset.

Критичные причины:

- нижний запас ленты в keyboard-open состоянии был привязан слишком грубо;
- итоговая посадка последнего сообщения не всегда доезжала до правильной позиции сразу;
- часть промежуточных экспериментов улучшала финальное положение, но давала рывок по пути;
- debug overlay помог локализовать проблему, но сам в проде уже не нужен.

## Что реально вошло в код

Ниже только значимые изменения, без шумных временных логов.

### Friend-actions

Вошло:

- глобально проброшен debug helper для chat friend actions;
- глобально проброшен comparer `peerChatIdsEqual` для friend helper-веток;
- remove-path снова проходит весь optimistic flow и затем подтверждается API.

Практический результат:

- `+` / `−` снова отрабатывают;
- список друзей и кэш контактов обновляются без runtime-падения.

### iOS PWA chat keyboard

Вошло:

- расчёт нижнего запаса ленты для iOS PWA переведён ближе к реальной высоте видимого composer, а не к "сырому ощущению клавиатуры";
- добавлен поздний добор до нижней позиции после открытия клавиатуры, если чат и до фокуса был у нижней границы;
- несколько неудачных snap/focus экспериментов были откатаны, чтобы не сохранить дёргание или пропадание composer;
- итоговый зазор между последним сообщением и строкой ввода уменьшен;
- временный `chat-overscroll` debug overlay полностью удалён.

Практический результат:

- последнее сообщение больше не остаётся наполовину под полем ввода;
- посадка стала ближе к ожидаемой;
- временный debug UI не торчит в интерфейсе.

## Что сознательно не оставляли

В ходе отладки было много временных шагов. В документации их не надо считать "состоянием системы".

Сознательно не считаем частью финального решения:

- экранные debug-overlay для friend-actions;
- экранные debug-overlay для overscroll;
- промежуточные copy/focus хаки, нужные только для съёма логов;
- слишком агрессивные snap-to-bottom варианты, которые вызывали рывки;
- широкие эксперименты по repair iOS PWA path, которые потом были откатаны.

## Что важно помнить дальше

### Правило по чатовым фиксам

Для chat/push/focus-фиксов сохраняется рабочее правило:

- каждый отдельный фикс поднимает `data-app-version` на `+0.001`;
- фикс сразу коммитится и пушится в `main`;
- в документации надо оставлять только финальное состояние, а не всю шумную цепочку гипотез.

### Практический вывод по iOS PWA

Для этого участка безопаснее работать так:

1. Не трогать широко весь keyboard path, если проблема локальна в final positioning.
2. Любой новый эксперимент делать узким и обратимым.
3. Если фикс улучшает финальную посадку, но добавляет рывок, такой фикс не оставлять.

### Дополнительное правило после позднего регресса

Позже в проекте был подтверждён отдельный PWA-регресс, вызванный уже не самим PWA path, а тем, что Telegram-specific hard-disable логика случайно стала доступна и для PWA composer.

Подтверждённый вывод:

1. любые Telegram-only keyboard/composer bypass-ветки должны быть жёстко ограничены Telegram runtime;
2. нельзя оставлять их как “общие чатовые” guard'ы;
3. иначе PWA перестаёт идти по своему штатному `visualViewport / pad / dock` сценарию и получает старые симптомы подъёма строки.

Фикс, который подтвердил это правило:

# Chat Fix Addendum — 2026-04-21

## Что добрали после предыдущего отчёта

После цикла `1.902–1.904` работа по чату продолжилась уже не в формате общей отладки keyboard path, а как серия маленьких прод-фиксов поверх рабочего состояния.

Подтверждённые изменения:

- `1.974–1.980` — серия точечных правок нижнего зазора между последним сообщением и composer в iOS PWA;
- `1.981` — убрано многошаговое дёргание ленты при подъёме клавиатуры;
- `1.982` — стабилизировано первое открытие чата с картинками;
- `1.983` — устранён сценарий, когда на первом кадре показывался урезанный history snapshot, а затем “пропавшие” старые сообщения дорисовывались позже;
- `1.985–1.986` — ускорена и стабилизирована гидрация меты собеседника в личке, особенно в шапках входящих сообщений;
- `1.987` — в личном диалоге доставленные сообщения стали стабильно получать две серые галочки;
- `1.988` — открытие диалога и preview переведено на более быстрый cached-first путь, включая disk snapshot.

## Итоговое состояние на текущий момент

Сейчас рабочее состояние по личкам и PWA такое:

- последнее сообщение в iOS PWA садится близко к composer и не уезжает под него;
- при открытии клавиатуры лента поднимается без лишнего промежуточного рывка;
- чат с картинками при первом открытии меньше подпрыгивает на догрузке медиа;
- при входе в диалог не должно быть эффекта “последних старых сообщений ещё нет, потом появились”;
- в личке одинаковая мета собеседника переиспользуется по всей ленте, а не догружается как будто отдельно для каждого сообщения;
- delivered-state в личке визуализируется двумя серыми галочками раньше, без ожидания read;
- диалог и preview открываются заметно быстрее за счёт мгновенного локального snapshot.

## Главные инженерные выводы

### 1. Для PWA keyboard path опасны не только неверные offset, но и многошаговые пересчёты

Подтверждённый вывод:

- проблема была не в самом факте подъёма ленты;
- проблема возникала, когда разные ветки одновременно меняли `padding`, `scrollTop` и top-offset;
- один финальный пересчёт надёжнее, чем серия “подправляющих” движений.

### 2. Для мгновенного открытия диалогов нельзя опираться только на live fetch

Подтверждённый вывод:

- ожидание сети создаёт ощущение медленного чата даже при исправной логике;
- cached-first render из RAM/disk snapshot даёт лучший первый кадр;
- live fetch должен тихо уточнять состояние, а не быть обязательным условием появления ленты.

### 3. Для лички одинаковую peer-meta надо нормализовать один раз на весь thread

Подтверждённый вывод:

- в 1:1-диалоге имя, `Poker21 id`, avatar и respect не должны вести себя как per-message payload;
- правильнее собрать лучшую известную meta о собеседнике один раз и распространять её на входящие сообщения до render;
- это ускоряет первый кадр и убирает ощущение “каждое сообщение отдельно прогружается”.

### 4. Самый дешёвый способ ускорить delivered-state — не ждать лишний GET ради UI-подтверждения

Практический вывод на текущий момент:

- perceived delivery в чате чаще всего тормозит не сеть сама по себе, а то, как UI ждёт подтверждение;
- если подтверждение уже известно клиенту, его лучше сразу отрисовывать локально;
- это ускоряет интерфейс без роста bandwidth.
