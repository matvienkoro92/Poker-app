# Комплексный аудит после исправлений

Дата: 5 сентября 2026. Локальное рабочее дерево, версия 4.002. Это повтор широкого продуктового и инженерного аудита: интерфейс, архитектура, безопасность, согласованность данных, производительность, тестирование и эксплуатация.

Код приложения в рамках этого аудита не менялся. Production API, реальные переписки, платежи и персональные данные не использовались. Новые воспроизведения выполнялись на исходных функциях с контролируемыми локальными заменами Redis/Blob/сети; существующие интеграционные тесты дополнительно запускались на настоящем изолированном Redis.

## Общий вывод

Проект имеет работающую инженерную основу: автоматическую сборку, CI, ограничения ресурсов, контрактные и браузерные проверки, проверку настоящего Redis и обновления PWA. Исправления предыдущего этапа подтверждаются. Вместе с этим защита от гонок и частичной записи пока неоднородна: рядом с защищённым бонусным журналом остаётся обычный read-modify-write в переводах.

Главные следующие задачи — целостность сделок, приватность вложений, завершение цепочки проверки бонусных списаний и повышение достоверности проверок интерфейса. Переписывать приложение целиком для этого не требуется. Нужны небольшие явно определённые контракты критических операций и проверки их отказов.

Это выборочный глубокий разбор критических путей, а не доказательство отсутствия других дефектов во всех 93 API-обработчиках.

## Подтверждённые замечания

### 1. P1 — завершение перевода не защищено от гонки и частичного сохранения

Места: `lib/api-handlers/transfers.js:550–555`, `831–855`.

`markReceived` читает состояние `seller_transferred`, затем отдельно сохраняет `completed` и увеличивает счётчики покупателя и продавца. Проверка состояния не связана атомарно с изменением. `saveTransfer` использует обычный pipeline.

Два воспроизведения на исходной функции с управляемым адаптером Redis:

- Два одновременных подтверждения прочитали прежнее состояние, оба вернули HTTP 200; счётчик каждого участника увеличился на 2 вместо 1.
- После сохранения `completed` и увеличения первого счётчика отказала следующая запись. Ответ — HTTP 503, сделка уже `completed`, счётчики — 1 и 0. Повтор — HTTP 409, поэтому обычный повтор не восстанавливает согласованность.

Это доказательство ошибки состояния и статистики сделок. Двойное фактическое списание денег этим сценарием не показано: деньги и фишки здесь подтверждают участники.

Решение: атомарный переход из ожидаемого состояния с записью счётчиков; стабильный результат повторного подтверждения. Проверить также гонки «взять/отменить» и истечение резерва. Уведомления привязать к единственному успешному переходу.

Критерий готовности: 10 одновременных подтверждений дают один переход и +1 каждому участнику; ошибка любого ключа не оставляет частично завершённую сделку.

### 2. P1 — вложения личных сообщений не имеют приватности на уровне файлового хранилища

Места: `lib/chat-image-blob.js:22–39`; `lib/chat-route-post-send.js:150–154`; `lib/api-handlers/chat-image.js:29–43`.

Изображения, голосовые и PDF используют общий загрузчик с `access: "public"`. Загрузчик получает ID отправителя, но не состав участников или права на переписку. Тот же путь вызывается для личного сообщения. Локальная подмена Blob SDK подтвердила отправку параметра `public`.

Следствие при подключённом публичном Blob-хранилище: человек, знающий URL вложения, может открыть его вне авторизованного чата. Случайная часть URL затрудняет угадывание, но не отзывает доступ после пересылки ссылки. Сам факт утечки или перебора ссылок не установлен.

Резервный proxy `chat-image` проверяет факт входа и домен Blob, но не право пользователя на конкретное сообщение. Простого переключения на private поэтому недостаточно.

Решение: хранить принадлежность вложения сообщению/диалогу, проверять участника при выдаче, использовать приватное хранение и авторизованный доступ. Отдельно определить судьбу ранее опубликованных вложений: изменение настройки новых загрузок не закрывает старые URL.

Критерий готовности: участник диалога получает вложение; посторонний пользователь и аноним — отказ; удаление/ограничение доступа имеет проверяемый результат.

### 3. P2 — старое списание может быть видно в журнале, но недоступно для проверки

Места: `lib/api-handlers/admin.js:504–509`; `lib/bonus-ledger.js:212–226`.

Отчёт по периоду уже читает всю сохранённую историю. Однако `handleBonusIssueReview` ищет нужный ID через `getBonusDebitOperations(5000)`, который берёт только первые 5000 элементов глобального списка, включая начисления. После достаточного числа новых операций старое списание получает «Списание не найдено», хотя его JSON существует. Пагинация журнала теперь может дойти до записи за этой границей.

Вывод подтверждён ограничением в пути кода; количество операций в production не измерялось.

Решение: читать конкретную запись по ID с проверкой её типа и прав администратора. Проверить операцию за пределами первых 5000 записей и запись, ранее выпавшую из старого индекса.

### 4. P2 — изменение проверки бонуса не инвалидирует расчёт возвратов

Места: `lib/api-handlers/admin.js:515–519`; `lib/bonus-ledger.js:17`, `468–499`.

Проверка сохраняется в `bonus_issue_reviews`. Ключ кэша итогов зависит от версии бонусного журнала; обработчик проверки эту версию не увеличивает. TTL по умолчанию — 30 секунд.

Локальное воспроизведение: отчёт рассчитан с возвратом 0; проверка изменена на `plus, amount=20`; повторный запрос вернул 0. После изменения версии журнала тот же расчёт вернул 20.

Итог: сразу после действия администратора расчёт способен показать старую сумму. Проверка версии до/после чтения также не замечает одновременное изменение review. Это не постоянная потеря данных: после истечения кэша сумма пересчитывается.

Решение: атомарно сохранять review и увеличивать версию расчёта, используемую всеми инстансами. Проверка — немедленный повтор отчёта после изменения review и изменение review во время расчёта.

### 5. P2 — первая сессия аналитики теряется после временной ошибки сети

Место: `app-analytics.js:55–61`.

`lastSessionFingerprint` запоминается до успешной отправки `session_started`. Ошибка сети превращается в `{ok:false}`, но fingerprint остаётся. Следующие вызовы в том же документе для той же сессии/пользователя пропускают отправку.

Воспроизведение исходного клиентского модуля: первый fetch завершился ошибкой; следующий вызов вернул `skipped:true`; всего сделан один запрос.

Это может занижать число зарегистрированных сессий при плохой сети. Размер искажения реальной аналитики не определён. Доказательства искажения конкретного бизнес-отчёта нет.

Решение: отдельно хранить выполняющийся запрос и подтверждённую отправку; повторять после ошибки с тем же event_id, чтобы серверная дедупликация сохранялась.

### 6. P2 — визуальный release gate может принять экран загрузки за готовый экран

Место: `scripts/smoke-visual.js:156–191`; артефакт `tmp/visual-smoke/profile.png` последнего успешного release-check.

Проверка проверяет активный view, размеры, навигацию, текст, переполнения и размер PNG. На снимке профиля при этом виден перекрывающий экран «ЗАГРУЖАЕМ ПРОФИЛЬ» с подписью «Готово». Проверка прошла. На снимке чата остаются skeleton-полосы.

Внешние запросы в тесте намеренно получают 503, поэтому эти снимки не доказывают зависание рабочего профиля. Они доказывают ограниченность gate: зелёный результат ещё не означает, что пользователь получил готовые данные или понятное завершённое состояние ошибки.

Решение: отдельные устойчивые fixtures для успешного, пустого, запрещённого и аварийного ответа; ожидание готовности конкретного раздела; запрет бесконечного loader; проверка кнопки повтора. Снимки не заменяют проверки пользовательского действия.

## Безопасность и границы окружений

Подтверждены ранее добавленные проверки Telegram, ограничение попыток, атомарное потребление кода, отзыв PWA-сессий и защита выдачи сессии от гонки смены пароля. Свежий npm audit сообщает 0 известных уязвимостей зависимостей. Это не распространяется автоматически на бизнес-логику или права на вложения.

Два дополнительных риска требуют отдельного контроля:

- `index.html:647` задаёт фиксированный удалённый API в `data-api-base`; `app-api-tracking.js:17–22` отдаёт ему приоритет над текущим origin. Обычный локальный/preview-запуск поэтому не изолирован автоматически от общего backend. Smoke-тесты блокируют внешние запросы, мобильный тест дополнительно убирает атрибут. Нужны явные настройки development/staging/production и тест, что preview не обращается к рабочему API. В данном аудите обращения к нему были заблокированы.
- PWA восстанавливает состояние `verified` из локально сохранённой сессии (`app-pwa-auth-restore.js:31–57`). Централизованного клиентского обработчика `session_revoked` не найдено. Сервер закрывает доступ, однако UX после отзыва требует отдельного браузерного сценария: очистка старой сессии и понятный вход заново, без восстановления прежней записи. Это риск интерфейса; обход серверного отзыва не обнаружен.

## Продукт и пользовательский интерфейс

Главная имеет узнаваемый визуальный стиль, выраженную основную кнопку и понятную нижнюю навигацию. На свежем снимке 390×844 отсутствует горизонтальное переполнение; основной блок не скачет при появлении новостей. Чат явно выделяет контакты администраторов.

Наблюдения по доступным снимкам и коду:

- Главный визуальный приоритет — раздача дня. Если бизнес-цель — возвращение к игре, это согласованно. Если цель — быстро выбрать ближайший турнир или решить вопрос с аккаунтом, эти сценарии стоит проверить отдельным пользовательским тестом.
- В гостевом заголовке подсказка об аккаунте обрезается до «ПРИВЯЖИТЕ АККА…». Более короткое понятное действие лучше объяснит следующий шаг.
- Розыгрыши доступны и в верхней панели, и среди карточек. Это может быть оправдано частотой использования; данных, подтверждающих необходимость дублирования, в аудите нет.
- При подменённом отказе API главная показывает «Доступна сейчас!» рядом с незагруженным итогом «Выиграно уже — ₽». Следует разделить постоянное рекламное описание и подтверждённую доступность действия, если последняя зависит от сервера.
- Ошибка, пустое состояние, загрузка и необходимость повторного входа нуждаются в одинаковом понятном завершении во всех разделах.

Конверсия, удержание и полезность функций не измерялись. Численная оценка UX «из 10» на основании этих данных была бы субъективной. Доступность для screen reader, увеличение текста, клавиатурный фокус и контраст не прошли отдельную проверку; отсутствие горизонтального overflow не является проверкой доступности.

Поэтому зелёный release gate не запрещает существенное замедление при сохранении размера файлов.

Для реального вывода нужны несколько прогонов, p50/p95 по рабочим устройствам и раздельные измерения Telegram WebView, Safari/PWA, холодного/тёплого кэша. Рабочая сеть и реальные устройства в этом аудите не проверялись.

## Архитектура и поддерживаемость

В корне — 186 frontend app*.js и 74 CSS-файла; в lib/api-handlers — 93 обработчика. Среди крупных файлов: CRM runtime — 5745 строк, admin reports — 5208, raffles — 4397, chat user modal — 4356, legacy reports — 4102.

Полезные свойства: разбиение по доменам, lazy loader, манифесты, отдельные HTML-фрагменты, единый API-роутер и уже выделенные общие механизмы авторизации/атомарности.

Стоимость изменений повышают глобальные переменные, взаимодействие через DOM ID и зависимость от порядка подключения. Наличие отдельных файлов ещё не означает независимость модулей. Ранее найденные разорванные CSS-правила — конкретный пример того, почему механическое разрезание файлов требует проверки границ и каскада.

Рекомендуемая последовательность рефакторинга:

1. Общий контракт переходов состояний для финансово значимых операций: ожидаемое состояние, атомарная запись, результат повторного запроса.
2. Явный слой запросов и ошибок авторизации на клиенте.
3. Один сложный домен за раз: init/load/dispose, зависимость через аргументы, проверяемое освобождение обработчиков и таймеров.
4. Только затем дальнейшее дробление крупных файлов. Размер файла сам по себе не является дефектом поведения.

## Эксплуатация и восстановление

CI включает сборку, проверку инструментов, настоящий Redis и release gate. Версия PWA и статического кэша согласованы; тест перехода со старого worker уже добавлен. Это снижает риск публикации несовместимой оболочки.

Что не подтверждено:

- Backup Redis/Blob и реальное восстановление состояния. `scripts/backup.sh` копирует файлы проекта в соседний каталог того же окружения; это не резервная копия рабочей базы и не проверка восстановления после потери хоста. Настройки резервирования провайдеров не исследовались.
- Заданные RPO/RTO, назначенный порядок сверки незавершённых финансовых операций и проверенная процедура восстановления.
- Рабочие оповещения о росте 5xx, отказах OTP, зависших операциях и деградации мобильной скорости. Наличие console.error не подтверждает мониторинг инцидентов.
- Android APK: Java в текущем окружении отсутствует, полноценная сборка и проверка устройства не выполнены.

Полное чтение бонусной истории исправило достоверность, но увеличивает стоимость отчёта. SCAN ограничен 2000 страницами и 20 секундами; дальнейшие чтения тоже требуют времени. При росте базы нужен индекс по времени/проверяемые агрегаты и отдельный нагрузочный тест на реалистичном объёме. Не следует снимать защитное прерывание ради выдачи неполного отчёта.

## Очерёдность следующей работы

1. Атомарные переходы переводов и безопасные повторы.
2. Приватность вложений личных сообщений с проверкой участников и планом для старых файлов.
3. Полная цепочка проверки бонусов: прямое чтение ID и версия кэша при изменении review.
4. Проверки готовности/ошибки интерфейса и сценарий отозванной PWA-сессии.
5. Повтор доставки аналитики и явное разделение окружений.
6. Мобильный performance gate, нагрузочный профиль отчётов и проверка восстановления данных.

Первые четыре пункта дают наибольший эффект для корректности и доверия пользователя. Оптимизацию дизайна и дальнейшее дробление файлов стоит делать с измеримыми критериями, после этих изменений.
