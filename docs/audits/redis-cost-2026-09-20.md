# Аудит расходов Redis — 20 сентября 2026

## Границы достоверности

Исследованы локальные frontend/backend, расписание Vercel, Redis-обёртка, кеши и приложенный скриншот Upstash. Production-логи по endpoint, Cost Explorer, размеры production-ключей и cache hit rate не получены. Поэтому ниже подтверждены механизмы расходов, но НЕ доля каждого endpoint в фактическом счёте. Период скриншота не указан. Нельзя считать все цифры месячным темпом или экстраполировать их на конец месяца без периода.

Локальные изменения ленивой загрузки, исправления недельных сумм и сводки новостей ещё не опубликованы в рамках этих задач. Аудит различает эти изменения и оставшиеся серверные расходы. Статические JS/WebP с Vercel не являются автоматически bandwidth Upstash.

## Счёт

На скриншоте 39 215 666 чтений + 5 893 332 записей = 45 108 998 команд. Чтения — 86,94%, записи — 13,06%. При $0,20/100 тыс. это $90,218 — близко к показанным $90,15; расхождение возможно из-за времени обновления счётчиков. Перерасход bandwidth: (601−200)×$0,03 = $12,03. Строка Other — $12,23, поэтому оставшиеся $0,20 нельзя без детализации назвать трафиком.

Команды — около 88% показанного счёта $102,38. Каждые убранные 1 млн команд экономят $2; 100 ГБ сверх включённого объёма — $3. Сокращение bandwidth до 200 ГБ при прежнем числе команд сэкономит около $12, а не большую часть счёта.

Тариф проверен: https://upstash.com/pricing/redis . Pipeline объединяет HTTP-запросы, но не превращает N Redis-команд в одну: https://upstash.com/docs/redis/features/restapi .

## Приоритеты по подтверждённым механизмам

### 1. Публичные данные CRM и аватары: высокая вероятность лишнего bandwidth

Код: lib/api-handlers/player-crm.js:405–460, 958–1040, 4003–4008; lib/public-avatar.js.

buildPublicPokerLevelRows читает 14 общих hash-структур (через redisCursorReadPipeline), затем MGET аватаров всех выбранных аккаунтов. row.avatarUrl получает исходное значение, включая data:image/base64. writePublicPokerLevelRowsCache сохраняет всю структуру rows в Redis. При avatarFormat=url преобразование идёт только после чтения/построения этого кеша. Следовательно, даже компактный ответ клиенту не устраняет чтение и повторную запись изображений внутри Redis.

Есть полезные ограничения: память процесса, общий Redis-кеш на 15 минут и HTTP-кеш. Поэтому нельзя умножать полный пересчёт на каждый визит. Реальный расход определяется cache hit rate, холодными процессами, инвалидациями и размером кеша.

Решение: хранить в публичном кеше только accountId, отображаемое имя, уровень, avatarVersion и URL; оригиналы изображений — в object storage/CDN. Версию аватара записывать при загрузке, а не вычислять хеш из полного base64 при чтении. Поддержать старые форматы на период миграции. Не увеличивать публичный TTL без корректного versioned URL: сейчас v присутствует в URL, но обработчик возвращает текущее изображение, а не историческую версию.

Модель, не замер: 1000 аватаров по 50 КБ = 50 МБ на один полный обход; 1000 обходов = 50 ГБ. Base64 увеличивает объём исходных бинарных данных примерно на треть. Для решения нужен STRLEN кеша, число его чтений и доля data:image в исходных аватарах.

### 2. Чат: стоимость пустого ожидания, а не только сообщений

Код: app-chat-polling.js:17–29; lib/chat-route-get-updates.js:189–215; lib/api-handlers/chat-runtime.js:265, 996, 1071, 1221.

Long poll удерживает HTTP-запрос до 45 секунд, но внутри продолжает обращаться к Redis каждые 5 секунд. Обычная ревизия общего чата — 3 команды, личного — 4; контакты дополнительно HMGET. У админа и на проверках доступа возможны дополнительные операции. Увеличение длительности HTTP long poll само по себе эти Redis-чтения не отменяет.

При совмещённой проверке личного чата и контактов получаем ориентировочно 5×720 = 3600 команд на пользователь-час непрерывного ожидания плюс начальные чтения, авторизация, присутствие и фактические сообщения. 1000 таких часов — около 3,6 млн команд, $7,20. Это модель, не фактическое число активных пользователей.

Решение первого этапа: единая компактная ревизия для выбранного диалога/контактов; один HMGET вместо нескольких команд; прекратить дублирующий polling разных вкладок через BroadcastChannel/leader tab; backoff при бездействии, остановка в скрытой вкладке там, где push уже покрывает уведомления. Второй этап — push/realtime, чтобы пустое ожидание не читало Redis. Риски: read receipts, редактирование/удаление сообщений, изменение доступа, заявки и непрочитанные должны менять ревизию, а не только новые сообщения.

Положительный факт: под-секундный серверный опрос уже заменён на 5 секунд; фоновые сводки чата уже ограничены 5/30 минутами. Это нельзя выдавать за новую экономию.

### 3. Недельные выдачи: полный обход при промахе короткого кеша

Код: lib/api-handlers/raffles.js:1458–1505, 4998–5004.

loadCurrentWeekRaffleIssueTotals читает generation, кеш, список ВСЕХ raffle IDs и GET каждой записи партиями по 80. TTL результата — 300 секунд. Недельная сводка зависит от даты действия с победителем, поэтому простое ограничение датой самого розыгрыша будет ошибочным: выдать старый приз можно на этой неделе.

Для N записей холодный расчёт — порядка N+4 команд, плюс инвалидации/авторизация. При N=1000 и непрерывном востребовании после каждого истечения TTL: около 288 тыс. команд/день, 8,6 млн за 30 дней ($17,3). Если запрос редкий, расход значительно меньше. Это верхняя модель активного использования, не замер.

Решение: журнал действий выдачи/возврата с idempotency key, недельные агрегаты и поколения; пересчёт только изменившихся недель. Нужна корректная обратная проводка при отмене статуса, исправлении суммы и повторном запросе. Финансовую точность ради кеша не ухудшать. Один безопасный backfill, затем инкрементальные обновления и периодическая сверка.

### 4. Архивы розыгрышей: lazy UI не равен lazy backend

Код: lib/api-handlers/raffles.js:4349–4495; полный list около 6415; app-raffles.js:2977, 3243.

Локально вкладка завершённых переведена на маленький список последних результатов. Но сервер при промахе archive-index строит index, месяцы и недели и сохраняет полные записи недель. Запросить одну маленькую страницу может означать холодный обход всего набора и запись множества кешей. Активные кеши имеют TTL 20 секунд (обычный) / 8 секунд (админ); некоторые клиентские действия явно обходят кеш.

Решение: постоянные индексы month/week -> IDs, отдельные summary-записи, инвалидация затронутой недели/месяца вместо всего архива; отдельный endpoint статистики лидеров. Открытие лидеров пока оставляет полный путь. Предотвратить параллельную перестройку одного кеша через короткий lock/single-flight. Критерий: открытие одного месяца не делает GET всех исторических raffle records.

### 5. Daily Poker: дорогой fallback полной истории

Код: lib/api-handlers/promo.js:1449–1515; кеши около 176–233 и 916–1016.

В пути полного списка победителей есть SMEMBERS всех пользователей, LRANGE всей истории игр каждого, затем чтение всех найденных games и последующая агрегация/обрезка. limit в ответе не ограничивает уже выполненные чтения. Существуют кеши на 24 часа и пути по датам — это важная защита; фактическая доля тяжёлого fallback требует логов.

Решение: использовать уже имеющиеся индексы по датам и агрегаты день/игрок/приз, latest winners хранить отдельно. Повторно не читать всю историю при каждом изменении текущего дня. Проверять исправления и идемпотентность начислений.

### 6. Глобальные hash-таблицы CRM

Код: lib/api-handlers/player-crm.js:158–182, 468, 958, 1633, 1730.

HGETALL часто заменяется на hscanall, а SMEMBERS — на sscanall. Это ограничивает размер отдельного ответа, но если курсор вычитывается до конца, общий объём не уменьшается; команд может стать больше. На одних экранах есть кеши и scoped population, однако широкие ветки остаются.

Решение: сначала выбрать страницу/список accountId, затем HMGET только нужных полей. Поиск — отдельный индекс, а не обход всех профилей. Не оптимизировать только текст команды HGETALL: оценивать все страницы HSCAN одной пользовательской операции.

### 7. Раздачи и их красная точка

Код: app-my-summary.js:11–75, 530; lib/api-handlers/starting-hands.js:11–47.

При первом определении непрочитанного загружается action=list; затем раз в минуту — action=version. Исправление отметки просмотра уменьшает localStorage и ошибки интерфейса, но само по себе почти не экономит Upstash. initial list читает потенциально большой JSON даже если график не открывают.

Решение: до открытия графика читать только version/count/updatedAt; хранить просмотренную версию. Загружать list исключительно при открытии. Не использовать изменение служебных полей как новое непрочитанное событие. Для больших списков — период, страницы и отдельные агрегаты графика.

### 8. Приватный кеш и ставки: часть расходов остаётся на сервере

Код: lib/api-handlers/private-cash.js:988, 1058; lib/api-handlers/tournament-bet.js:199, 402–429; app-tournament-bet.js:16, 526.

Локально архив приватного кеша теперь возвращает метаданные, участников — по выбранной игре. Но сервер по-прежнему читает каталог event records, чтобы определить статусы. Индекс активных IDs устранит этот остаточный обход.

История ставок теперь запрашивается отдельно в окне. Однако mode=home и achievements всё ещё читают историю для сводок/рейтинга, а окно обновляется каждые 15 секунд. Нужны готовые home/rating summaries, event version и polling только активного видимого события. Не подменять рейтинг подсчётом по последним событиям.

## Что не стоит делать первым

* Не отключать все cron: две ежеминутные очереди используют bounded ZRANGEBYSCORE. Если обе пустые и выполняют по одной команде, это 86 400 команд/30 дней, около $0,17. Обработка непустых очередей считается отдельно. Их отключение ломает доставку и меню ради небольшой базовой экономии.
* Не чистить 1 ГБ данных только ради счёта за storage: на текущем PAYG первый 1 ГБ бесплатный. Удаление истории не устраняет повторные запросы и может испортить бухгалтерию.
* Не рассчитывать на pipeline как на снижение billed commands.
* Не увеличивать TTL персональных ответов общим публичным кешем. Авторизацию и персональные статусы отделить от публичных агрегатов.
* Не считать все setInterval сетевыми: многие лишь перерисовывают секундомер.
* Не считать перенос статистической сводки из JS в JSON экономией именно Redis: данные рейтинга были статическими; это прежде всего экономия CDN/браузерного трафика.

## Почему сейчас нет достоверного распределения счёта

lib/redis.js пишет предупреждение для pipeline >=50 команд, но не измеряет суммарный размер ответа и частоту каждого context. Мелкий горячий запрос на 5 команд может стоить больше редкой большой пачки. Guard ограничивает формы запросов, не реальные байты; HGETALL/SMEMBERS в основном предупреждают, GET огромного JSON может пройти. Часть модулей использует собственные REST-пути, поэтому одна обёртка не гарантирует полного учёта.

Нужна телеметрия на 24–48 часов: endpoint + operation context, число команд по типу, request/response bytes, latency, cache hit/miss, retries, HTTP status; без ключей с ID, значений и токенов. Сэмплирование, агрегация в памяти и отправка в существующие логи/observability, НЕ дополнительный INCR в Redis на каждую команду. Response bytes обёртки — оценка приложения, сопоставлять с биллингом, а не называть точным billed bandwidth.

Составить два независимых топа: commands/day и Redis response bytes/day. Снять bounded STRLEN/HLEN/LLEN известных ключей: public_levels_cache, profile hash, raffle records/IDs, starting-hands list. Не запускать массовый GET всех данных или MONITOR для первоначального аудита.

## План реализации и критерии

1. Телеметрия и базовая линия; CRM cache без base64; unread через version. Низкий/средний риск, легко сравнить одинаковые действия до/после.
2. Чат: единая ревизия + отсутствие дублирующих опросов; weekly issue aggregates и archive indexes. Средний/высокий риск, тесты корректности статусов обязательны.
3. Daily Poker aggregates, private cash active index, готовые summaries ставок; миграция медиа в object storage с совместимостью старых ссылок.
4. Повторный замер при сопоставимом числе активных пользователей; экономия в командах/пользователь-час и bytes/операцию, а не только общем дневном счёте.

Цели на отдельные операции: CRM summary не содержит data:image даже в Redis-кеше; unread никогда не читает список раздач; недельная сводка в штатном запросе не читает весь список розыгрышей; закрытый архив не инициирует чтение записей; открытие одной недели ограничено её IDs; повторный просмотр неизменённого результата не пересчитывает историю.

Это не обещание экономии: общий результат зависит от реального вклада перечисленных путей. Fixed 1GB сейчас рекламируется за $20 с 100 ГБ bandwidth, но база уже около лимита памяти, а трафик 601 ГБ; тариф нельзя рекомендовать как готовое решение без точного размера, правил превышения и запаса. Fixed 5GB стоит $100 при 500 ГБ, поэтому сам по себе почти не улучшает текущий счёт. Сначала убрать повторную работу, затем сравнить планы по замеренному профилю.
