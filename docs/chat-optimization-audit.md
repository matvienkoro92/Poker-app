# Chat Optimization Audit

Дата: 2026-04-18

## Что уже сделали

### 1. Сильно ослабили polling
- Открытый чат перевели с агрессивного polling на более редкий режим.
- Список диалогов и hidden tab теперь обновляются заметно реже.
- Добавили burst-режим для активного треда, чтобы не терять ощущение живого чата.

Эффект:
- Меньше `reads`
- Меньше `bandwidth`
- Меньше бессмысленных одинаковых запросов

### 2. Убрали тяжёлый roster из регулярного общего чата
- `generalMembers` больше не едет на каждый обычный `mode=general` poll.
- Ростер грузится только когда он реально нужен.

Эффект:
- Заметное сокращение веса ответа общего чата
- Меньше исходящего трафика

### 3. Перевели unread в Redis counters
- Unread больше не считается через чтение всей истории тредов.
- Для личек, групп и общего чата используются отдельные счётчики.

Эффект:
- Сильное снижение стоимости `mode=contacts`
- Меньше Redis reads

### 4. Добавили diff-fetch для активного чата
- В burst-режиме клиент тянет не всю ленту, а только хвост после `afterId/afterTime`.

Эффект:
- Быстрее обновление открытого треда
- Меньше payload на коротких poll-запросах

### 5. Вынесли thread meta
- Сохраняем `lastMessageTime`, `lastMessageId`, preview.
- Список диалогов сортируется без чтения головы каждой message list.

Эффект:
- Дешевле и быстрее `contacts`

### 6. Клубное preview перевели на meta
- Preview общего чата больше не требует чтения полной ленты.

Эффект:
- Ещё меньше лишних чтений и перерисовок

### 7. Подрезали тяжёлые reads в contacts
- Убрали лишние чтения `visitors` / полного `visitor_usernames`.
- Добавили кэш статистики общего чата для списка диалогов.

Эффект:
- `contacts` стал заметно легче

### 8. Добавили push-triggered refetch
- Push теперь не только показывает уведомление, но и будит UI.
- После push чат сразу делает refetch активного треда и списка.

Эффект:
- Сообщения появляются быстрее
- Меньше ощущения задержки между push и обновлением чата

### 9. Добавили coalescing для push-refetch
- Серия push-событий схлопывается в один короткий refetch-цикл.

Эффект:
- Меньше лишних запросов
- Меньше дёргания UI

### 10. Ускорили первый рендер треда
- Первую загрузку урезали до 40 сообщений.
- Второстепенные обновления шапки/бейджей перевели в post-render.

Эффект:
- Быстрее открытие диалога
- Лучше ощущение на слабых устройствах

### 11. Сделали подгрузку старой истории по кнопке
- Старые сообщения теперь подгружаются только по `beforeId/beforeTime`.

Эффект:
- Быстрый initial load
- История грузится только когда реально нужна

### 12. Добавили incoming push placeholders
- В открытом чате можно увидеть временный incoming placeholder ещё до серверного fetch.

Эффект:
- Чат ощущается живее

### 13. Оптимизировали hot path burst-render
- Для частичных обновлений больше не считаем тяжёлую сигнатуру всей ленты.
- Рендер схлопывается в `requestAnimationFrame`.

Эффект:
- Меньше CPU при активной переписке
- Более плавный UI

## Что в итоге уже улучшили

По сути, мы уже закрыли почти все самые очевидные и дорогие проблемы MVP-чата:

- слишком частый polling
- слишком тяжёлые ответы общего чата
- дорогой unread
- дорогой `contacts`
- полный reload вместо diff
- тяжёлый initial load
- отсутствие demand-loading истории
- слабую реакцию UI на push

Если оценивать по практической ценности, уже сделано примерно:

- 70-80% главных оптимизаций по стоимости
- 60-70% главных оптимизаций по perceived performance

То есть чат уже стал сильно ближе к нормальной production-схеме, чем был изначально.

## Что ещё лучше бы сделать

### Приоритет 1. Append-path без полной пересборки innerHTML

Сейчас даже после оптимизации hot-path мы всё ещё часто полностью пересобираем HTML ленты.

Лучше сделать:
- append нового сообщения в конец
- prepend старых сообщений сверху
- полный rerender только как fallback

Эффект:
- ещё более плавный чат
- меньше layout/reflow
- особенно заметно на длинных тредах и слабых телефонах

### Приоритет 2. Ещё сильнее облегчить contacts

Хотя `contacts` уже сильно лучше, он всё ещё остаётся главным постоянным фоновым consumer.

Можно ещё сделать:
- отдельный lightweight list meta endpoint
- presence отдельным тонким слоем
- более редкий refetch списка при открытом треде

### Приоритет 3. Перестать читать весь тред для edit/delete/reactions

Сейчас там местами ещё используются тяжёлые пути через полный `LRANGE`.

Лучше:
- завести message index / lookup по `messageId`
- править точечно, без чтения всей истории

## Что бы я рекомендовал делать дальше по порядку

1. Добить click-through по push
2. Добить стабильность самих push-уведомлений
3. Сделать append/prepend-path вместо полной пересборки ленты
4. Ещё облегчить `contacts`
5. Перевести edit/delete/reactions на точечный доступ

## Общая оценка

Чат уже стал:

- заметно дешевле
- заметно быстрее
- намного ближе к масштабу `1000+` пользователей

Но для полностью “боевого” состояния всё ещё критично закрыть два пункта:

- надёжный переход по push в нужный чат
- надёжную доставку push

Push-open и базовая доставка уже были стабилизированы в следующем цикле, поэтому основной remaining work теперь именно в polish и cost reduction, а не в самом факте открытия нужного чата.
